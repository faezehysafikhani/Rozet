# زیرساخت بخش مدیریت پروژه (فاز ۰)

این فایل‌ها پایه‌ی فازهای بعدی صفحه‌های «مدیریت پروژه» هستند. همه فایل‌های جدیدند و `App.jsx` را تغییر نمی‌دهند.

| فایل | کاربرد |
|---|---|
| `src/utils/jalali.js` | تبدیل تاریخ میلادی (ISO) و شمسی، طول ماه، قالب‌بندی. با تقویم شمسی مرورگر برای سال‌های ۱۹۰۰ تا ۲۱۰۰ (۷۳٬۴۱۴ روز) مقایسه شده است. |
| `src/components/JalaliDateInput.jsx` | انتخاب‌گر تاریخ شمسی (روز / ماه / سال). مثل `<input type="date">` یک رشته‌ی ISO می‌گیرد و می‌دهد؛ تا کامل نشود مقدار خالی است. |
| `src/components/ConfirmDialog.jsx` | پنجره‌ی تأیید (برای حذف). `useConfirm()` یک `dialog` برمی‌گرداند که باید یک بار رندر شود. خطای عملیات داخل پنجره می‌ماند. |
| `src/features/project-management/pmApi.js` | تابع برای هر endpoint پروژه (پروژه، فعالیت‌ها، وابستگی‌ها، baseline، منحنی S، MS Project، پیشرفت، دلایل تأخیر، مستندات، خروجی‌ها، KPI، تاریخچه، تقویم، استراتژی، هم‌راستایی) و `downloadFile` برای دانلودهایی که توکن می‌خواهند. |
| `src/features/project-management/pmErrors.js` | `explainPmError(result)` پیام فارسی کد خطای Core؛ `toOutcome(result)` برای ConfirmDialog. |
| `src/features/project-management/hooks.js` | `useProjectList` (جست‌وجو، فیلتر، مرتب‌سازی و صفحه‌بندی سمت Core) و `useProjectResources(projectId, [...])` (فقط منابع درخواست‌شده را می‌گیرد). |

## قراردادها
- تاریخ در Core میلادی ذخیره می‌شود (`yyyy-mm-dd`)؛ فقط نمایش و ورود در UI شمسی است.
- هر صفحه فقط داده‌ی خودش را بارگذاری می‌کند (`useProjectResources`)، نه همه‌ی پروژه‌ها را.
- هر خطای Core با `explainPmError` فارسی می‌شود؛ هر دکمه بر اساس `can(...)` نمایش داده یا غیرفعال می‌شود.
- «ارسال برای تأیید»: اگر برای پروژه زنجیره‌ی تأیید تعریف شده باشد رکورد «در انتظار تأیید» می‌شود، وگرنه Core آن را مستقیماً «تأیید شده» می‌کند. برای ساختن زنجیره‌های پیش‌فرض یک بار `pmApi.applyApprovalDefaults()` را اجرا کنید.
- ویژگی‌های هوش مصنوعی Core (خلاصه‌ی مستند، تحلیل ارتباط، تولید WBS) در `Rozet.Api` پیاده‌سازی نشده‌اند (پاسخ 501) و در UI نیستند.

## فاز ۱ — مدیریت مستندات
`src/features/project-management/documents/` : فهرست (جست‌وجو، فیلتر نوع و وضعیت)، آپلود، دانلود، ویرایش عنوان/نوع، نسخه‌ها (فهرست، دانلود هر نسخه، آپلود نسخه‌ی جدید)، ارسال برای تأیید و حذف.
- هر دکمه فقط برای کسی نمایش داده می‌شود که دسترسی همان کار (`ProjectDocuments.*`) را دارد.
- Core برای مستندات پروژه نوع و حجم فایل را بررسی نمی‌کند؛ صفحه قاعده‌ی سراسری سامانه (`GET /api/platform/upload-policy`: فرمت‌های مجاز و حداکثر حجم) را خودش اعمال می‌کند.
- سندی که در انتظار تأیید است نسخه‌ی جدید نمی‌پذیرد (قاعده‌ی Core).

## فاز ۲ — تقویم پروژه
`src/features/project-management/calendar/` : تقویم ماهانه‌ی شمسی (شنبه تا جمعه) با ناوبری ماه/سال و دکمه‌ی «امروز»، برای یک پروژه یا همه‌ی پروژه‌ها (حداکثر ۴۰ پروژه).
- رویدادها از Core: موعد وظایف چابک، بازه‌ی فعالیت‌ها و اقدام‌ها، تاریخ هدف خروجی‌ها، شروع و پایان پروژه. هر نوع فقط برای کسی که دسترسی مشاهده‌ی آن را دارد بارگذاری می‌شود؛ بقیه حذف می‌شوند و صفحه می‌گوید چرا.
- روزهای غیرکاری از تقویم کاری پروژه (یا تقویم پیش‌فرض سازمان) و تعطیلات رسمی از `official-holidays`؛ بدون دسترسی به تقویم کاری، جمعه غیرکاری فرض می‌شود.
- با کلیک روی یک روز، جزئیات رویدادها (نوع، وضعیت، پروژه، مسئول، بازه) زیر تقویم می‌آید؛ رویداد معوق قرمز است و تکمیل‌شده‌ها کم‌رنگ.
- صفحه‌ی قبلی فقط در `TaskManagement` ثبت شده بود و از منوی «مدیریت پروژه» هرگز باز نمی‌شد (منوی «تقویم پروژه» صفحه‌ی برنامه‌ریزی را نشان می‌داد).

## فاز ۳ — چرخه‌ی پروژه (برنامه‌ریزی پروژه)
`src/features/project-management/projects/` : جدول پروژه‌ها و تمام چرخه‌ی عمر پروژه.
- فهرست از `GET /api/portfolio/projects` (با قوانین دیدپذیری سازمان؛ نیازمند `Portfolio.View`) و برای کسی که فقط `Projects.View` دارد از `GET /projects`. جست‌وجو (ارقام فارسی و لاتین یکسان‌اند)، فیلتر وضعیت/نوع/تأیید/واحد/مدیر، مرتب‌سازی، «نمایش آرشیو» و صفحه‌بندی ۱۰تایی سمت UI. ستون پیشرفت از `POST /projects/progress`.
- جزئیات پروژه، ایجاد و ویرایش (`ProjectFormDialog` با تاریخ شمسی؛ نوع پروژه بعد از ایجاد ثابت است)، تغییر وضعیت (پیش‌نویس/فعال/متوقف/تکمیل‌شده)، آرشیو، حذف (خطای ۴۰۹ Core با فهرست وابستگی‌ها نمایش داده می‌شود) و ارسال برای تأیید (اگر مجموع وزن فعالیت‌ها ۱۰۰ نباشد Core رد می‌کند و پیام فارسی نشان داده می‌شود).
- دسترسی‌ها: ایجاد `Projects.Create`، ویرایش/وضعیت `Projects.Edit`، آرشیو `Projects.Delete`، حذف `Projects.Remove`، ارسال `Projects.Submit`.
- انتخاب یک ردیف، پروژه‌ی منتخب را عوض می‌کند و جدول فعالیت‌های پایین صفحه (که در فاز ۴ بازنویسی می‌شود) همان پروژه را نشان می‌دهد.
- فرم جدید جای فرم ایجاد پروژه‌ی `CreateProjectItemModal` را می‌گیرد؛ آن کد در `App.jsx` دیگر از این صفحه صدا زده نمی‌شود.

## فاز ۴ — ساختار شکست کار (WBS) و زمان‌بندی
`src/features/project-management/schedule/` : جدول فعالیت‌های پروژه‌ی منتخب در صفحه‌ی «برنامه‌ریزی پروژه»، زیر جدول پروژه‌ها (جدول قدیمی فعالیت‌ها در `App.jsx` حذف شد).
- داده از `GET /waterfall/schedule` (فعالیت‌های ذخیره‌شده + مقادیر محاسبه‌شده‌ی زمان‌بندی) ساخته می‌شود؛ ردیف‌ها بر اساس شماره‌ی WBS (عددی) مرتب و به‌صورت درخت تو‌رفته نمایش داده می‌شوند و هر سطح قابل جمع/باز کردن است (جمع/باز کردن همه هم دارد).
- ستون‌ها: WBS، نام (نشان بحرانی، نماد نقطه‌عطف، علامت مدت فرضی)، مسئول، شروع و پایان شمسی، مدت، شناوری، وزن، پیشرفت برنامه‌ای و واقعی، پیش‌نیازها، وضعیت تأیید و عملیات.
- عملیات: افزودن فعالیت/زیرفعالیت و ویرایش (والد، وزن در حالت وزن‌دهی دستی، یک پیش‌نیاز با نوع و تأخیر)، ثبت پیشرفت واقعی، ارسال برای تأیید، حذف (حذف زیرفعالیت‌ها فقط پس از تأیید صریح)، «اعمال زمان‌بندی» و تنظیمات زمان‌بندی (در حالت ترکیبی مجموع ضرایب باید ۱۰۰ باشد).
- دسترسی‌ها: `WaterfallActivities.View/Create/Edit/Delete/Submit` و `WaterfallSchedule.Manage`؛ هر دکمه فقط برای دارنده‌ی دسترسی آن نمایش داده می‌شود. خطاهای انگلیسی Core (مثلاً وابستگی دوری) فارسی می‌شوند.
- بعد از هر تغییر، هم زمان‌بندی دوباره خوانده می‌شود و هم داده‌ی سراسری برنامه (`data.refresh()`) تا صفحه‌های قدیمی کهنه نمانند.
- اگر ثبت پیش‌نیاز بعد از ذخیره‌ی فعالیت شکست بخورد، فعالیت ذخیره می‌ماند و خطا جداگانه نشان داده می‌شود.

## فاز ۵ — خط مبنا، منحنی S و MS Project
`src/features/project-management/baselines/` : پنل «خط مبنا، منحنی S و MS Project» زیر جدول زمان‌بندی در «برنامه‌ریزی پروژه»، با سه زبانه؛ فقط زبانه‌ی باز داده‌اش را می‌گیرد.
- **خط مبنا**: فهرست نسخه‌های ذخیره‌شده‌ی برنامه (شماره، نام، نوع، تاریخ و ثبت‌کننده، بازه، تعداد فعالیت، پیشرفت)، ثبت نسخه‌ی جدید (نام، یادداشت، نوع «خط مبنا» یا «اطلاعات پیشرفت») و حذف. دکمه‌ی «مقایسه و جزئیات»:
  - مقایسه با برنامه‌ی فعلی (`/baselines/{id}/variance`): انحراف شروع و پایان پروژه، شمار فعالیت‌ها به تفکیک مطابق برنامه / با تأخیر / زودتر / افزوده‌شده / حذف‌شده (با فیلتر) و انحراف شروع، پایان و مدت هر فعالیت. انحراف‌ها با کلمه («۴ روز دیرتر») نوشته می‌شوند، چون علامت + و − جلوی رقم فارسی در متن راست‌به‌چپ جابه‌جا می‌شود.
  - محتوای نسخه (`/baselines/{id}`): درخت فعالیت‌ها با WBS، مسئول، تاریخ‌ها، وزن و پیشرفت همان روز.
- **منحنی S**: نمودار SVG پیشرفت برنامه‌ای (محاسبه‌شده‌ی Core از زمان‌بندی) و واقعی (نقطه‌های ثبت‌شده) با خط «امروز»، گام روزانه/هفتگی/دو هفته/ماهانه، کارت‌های برنامه‌ای/واقعی/انحراف و شاخص SPI (زیر ۱ یعنی عقب از برنامه). Core تاریخچه‌ی پیشرفت واقعی را فقط از نقطه‌هایی می‌سازد که کاربر ثبت می‌کند؛ پس «ثبت نقطه‌ی پیشرفت» (`/progress-snapshots`، برای یک تاریخ دلخواه و یادداشت) و حذف نقطه هم هست. ثبت دوباره برای تاریخی که نقطه دارد، نقطه‌ی قبلی را به‌روز می‌کند و UI قبل از ثبت همین را می‌گوید.
- **MS Project**: خروجی XML (دانلود با توکن، از طریق `downloadFile`) و ورود XML (حداکثر ۲۰ مگابایت). اگر پروژه فعالیت دارد، ورود فقط با «جایگزینی فعالیت‌های موجود» ممکن است و قبل از اجرا تأیید صریح می‌خواهد (Core پیش از حذف کل فایل را اعتبارسنجی می‌کند، پس فایل نامعتبر برنامه‌ی فعلی را خراب نمی‌کند). گزارش ورود (تعداد فعالیت و وابستگی، تعداد جایگزین‌شده و هشدارهای فارسی‌شده) نشان داده می‌شود و جدول زمان‌بندی خودکار دوباره خوانده می‌شود.
- دسترسی‌ها: مشاهده‌ی همه‌ی زبانه‌ها و خروجی XML با `WaterfallActivities.View`؛ ثبت/حذف نسخه، ثبت/حذف نقطه و ورود فایل با `WaterfallSchedule.Manage`.
- `DialogParts.jsx` (`Shell`, `Field`, `Footer`) از دیالوگ‌های فاز ۴ بیرون کشیده شد تا بین فازها مشترک باشد؛ رفتار دیالوگ‌های فاز ۴ تغییر نکرده است.
